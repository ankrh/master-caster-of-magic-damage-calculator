# P8.1 — MoM 1.31 Specials invocation arguments

Documentation/source reconciliation only. This ledger covers the two named MoM 1.31
call sites and local reset/retain witnesses. It adds no reconstruction, calculator change,
50-step migration or other caller inventory. All addresses are existing MoM 1.31 file
offsets; ranges are half-open. Canonical source is [unitcalc.c](unitcalc.c), supported by
[R6.1a](R6.1a.evidence.md), [R6.1b](R6.1b.evidence.md), [R6.1c](R6.1c.evidence.md) and
[R6.1d](R6.1d.evidence.md). [F277.1](F277.1.execution-census.md) supplies the corresponding
CP/CoM comparison; its zero-mutations second-call rule must not be imported into MoM 1.31.

## Source availability and the two calls

Let P denote permanent `_UNITS[].enchantments`, I the battle object's `item_enchantments`,
and B its `enchantments`. They are distinct fields. Subscripts below label reads at
different points; they do not assert an intervening mutation or establish outer-call identity.

| Required fact | Existing MoM 1.31 locator | Result / availability |
|---|---|---|
| Constructor body | R6.1b, `BU_Construct`, `0x8EDFD..0x8F310` | Complete existing body; no missing extent. |
| Constructor mutation argument | `0x8EE0C`, local `[bp-7]` | M1 is a saved permanent mutations byte. |
| Constructor enchantment arguments | `0x8F005`, locals `[bp-6]` / `[bp-4]` | Low/high halves of P1 OR I1. The 1.31 locator is **0x8F005**, not CP's 0x8F007. |
| First Specials invocation | `0x8F2A2` → `0x8F310` | The caller-supplied battle object, copied P1 OR I1 mask, M1; before the movement and HP assignments below. |
| Battlefield body | R6.1c `0x8FF09..0x90635`, R6.1d `0x90635..0x90B8E` | Complete existing body; no missing extent for this mapping. |
| Battlefield mutation argument | `0x90236`, separate permanent read | M2, the battlefield frame's saved mutations, not a forced zero and not an automatic reuse of M1. |
| Battlefield enchantment arguments | `0x909CB..0x90A09` | Per half, D = (P2 XOR B2) AND B2 = B2 AND NOT P2. P/B are read here; this is not subtraction of the first call's saved mask. |
| Second Specials invocation | `0x90A1D` → `0x8F310` | The caller-supplied battle object, copied D mask, M2; after the preceding battlefield modifiers and before Warp/Shatter/clamps. |
| Shared routine and argument layout | R6.1a, `0x8F310..0x8F881`; argument load `0x8F314` | Far bu at `[bp+6]`, mask low/high at `[bp+0xA]` / `[bp+0xC]`, mutation byte at `[bp+0xE]` loaded into CL. |

The source uses split low/high words in the constructor call and a packed conceptual uint32
in the battlefield call. These are transcriptions of the same binary argument layout, not
two recovered compilable C signatures. Current-call arguments are copied values: a later
write to B does not retroactively change the mask already passed to that invocation.
When an enclosing sequence supplies the same battle object, the two invocations operate on
its successive states. This local-call ledger does not prove that outer pointer identity
across opaque calls or independently initiated calculations.

A permanent bit present in P2 is excluded from D. An item-only bit is not excluded by this
formula: if it is also present in B2, both masks may contain it. This describes the masks;
it does not establish which item/battle combinations admission actually creates. Likewise
M1 and M2 are distinct snapshots; equality or a change between them is an input/history
question, not a fact inferred solely from the two reads.

These are local reset/retain witnesses, not an exhaustive field lifecycle. In particular,
the battlefield body retains and modifies running fields rather than promising every first-call
value survives unchanged. The separate HP helpers and initial object population are already
distinct source owners; this preparation does not rederive them or migrate their steps.

## Local Specials witnesses and the Holy Weapon distinction

| Existing MoM 1.31 row | Operation | What the local row establishes |
|---|---|---|
| True Sight, test `0x8F338`, write `0x8F34F` | OR Illusion Immunity into Attribs_1 | Repeating this particular OR with the same bit is idempotent; it does not make the entire routine idempotent or identify admission history. |
| Mutation armor, test `0x8F6D6`, writes `0x8F6E2/0x8F6F2/0x8F6FE` | Defense +=3, Gold_Defense +=3, race := Chaos | The row is additive on the fields present at each invocation. MoM 1.31 supplies mutations at both calls; whether the guard passes depends on each snapshot. This is not a blanket final-stat doubling claim after intervening modifiers. |
| Mutation wings, test `0x8F703`, writes `0x8F70F/0x8F71B` | OR Flying, race := Chaos | Bit setting and race assignment have different overwrite behavior from arithmetic. Later Web can clear Flying. |
| Mutation breath, test `0x8F720`, writes `0x8F728/0x8F730/0x8F738` | Ranged :=2, ranged type := Fire Breath, race := Chaos | Assignment, not +=2. A repeated invocation can overwrite an intervening ranged value. |

Holy Weapon/Holy Arms is **inline in the MoM 1.31 constructor**, with tests from `0x8F1A8`
through the block ending at `0x8F24E`,
before the first Specials call. Its grant writes B at `0x8F1E4/0x8F1E8`; its hit-modifier
increments are at `0x8F1EF` and the ranged-qualified `0x8F22F`. It is not a Holy Weapon row
inside MoM 1.31 Specials. The two Specials calls therefore do not license applying that
inline bonus twice. Reuse the existing constructor predicate, including the distinct
Holy Arms grant and copied-mask branch; later-build relocated tails belong to other versions.
