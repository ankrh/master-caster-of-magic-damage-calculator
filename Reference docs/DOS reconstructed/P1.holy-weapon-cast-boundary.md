# P1 — DOS Holy Weapon cast-boundary availability

Documentation/source reconciliation only. This maps the approved Holy Weapon pilot; it does
not add reconstructed binary code or authorize a calculator schedule. Primary existing sources include
[combat.c](combat.c), [unitcalc.c](unitcalc.c), [A32](A32.evidence.md), the
[F250.3 shared class-1/15 writer](F250.3.mind-truesight.evidence.md), and

## Pilot binding and existing local entry

All three versioned SPELLDAT.LBX files have record 124 at file `0x1394 = 0x224 + 124*0x24`:
name Holy Weapon, class byte +0x15 = 15, effect low/high words +0x20/+0x22 = 0/0x0080.
That mask joins existing `unitcalc.c::UE_HOLY_WEAPON = 0x00800000`; it is not a global grant.
The data was re-read independently for this reconciliation. Runtime loading and entry-index
meaning remain separate conditions. After the opaque entry call, named binding also requires
DI=124, the live spell-data mapping to select that record, and SI/the battle pointer to select
the intended target carrier; no register, pointer or memory preservation is inferred.

A32 already inventories the resolver dispatcher `0x81F4C..0x81F6F`; its current canonical C
has the class getter/dispatch locator, while the complete bytes and class table are retained
in the reviewed [F250.3 raw packet](F250.3.mind-truesight.raw.md). The class-15 table word at
`0x82F8F` is `FD 22` in all builds: with the packet's CS file base `0x80330`, it selects
`0x8262D`. Reuse this existing dispatch evidence; no new dispatcher body is derived here.

At `0x8262D`, the existing class-1/15 source pushes its six live frame/register arguments and
calls `0418:0043` at `0x8263D` before examining special spell indices. Under unchanged DI=124,
Holy Weapon avoids the old-build index70 and CoM indices77/94 special paths and reaches the
ordinary stores. Those conditions are local observations after an opaque call, not proof that
the original input survives it or that every unit is eligible.

## Remaining boundaries and design readiness

Incoming DI/SI and frame provenance and any pre-dispatch recalculation remain **unmapped**,
not established absent from existing source. Their exact missing extent and instruction count
are unknown. A locating-only check of human class-15 table word `0x86977` identifies MoM
`[0x85C70,0x85C79)` (2 instructions) and CP/CoM `[0x85C64,0x85C70)` (6 each), leading to
`0x85D0E`. The patched fragments fall inside A32's already inventoried target-type extent;
they must be subtracted before requesting new source. MoM's two-instruction candidate is
outside those listed A32 extents. This identifies the local type-setting
candidate, not the complete human target predicate; that predicate's missing size is unknown.

Start any needed follow-up lookup from these candidates and the existing resolver `0x81F4C`,
subtract A32/F250 coverage, and identify only the required class-15 input/target/timing seam.
Request approval for that bounded
source-availability/packet-preparation follow-up before new reconstruction, if the pilot design
actually requires that fact. F279.2 may retain explicit entry conditions for conditional
representation design; this does not settle faithful pilot admission or implementation. An
actually required unknown gate still blocks that specific claim. General runtime/frame
unknowns are not automatic design blockers. Do not request a whole loader or validator on
their strength.

In CoM, P1.1 establishes the aggregation connection; in MoM/CP,
it establishes only the remaining opaque calls and return. It cannot by itself settle full
target admission or pre-cast timing. A full calculator pass is therefore not yet
proved equivalent for the pilot. Any later comparison must retain persistent constructor
mutations, the actual target/all-slot scope and the exact post-call byte-7 restoration.
Generalization is limited to the existing ordinary class-1/15 body under its stated live-state
conditions; sharing a class does not prove every spell's full admission or outer schedule.

P1's approved inventory is complete. Review and validation are recorded in `.reviews/P1/`;
P1.1 supplies the bridge evidence; schedule implementation remains with its existing task owners.
