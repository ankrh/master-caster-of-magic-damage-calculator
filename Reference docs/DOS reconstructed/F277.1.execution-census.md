## Invocation and argument boundary

Let P be persistent `_UNITS[].enchantments`, I battle `item_enchantments`, B battle
`enchantments`, and M the constructor's saved mutations byte. These are distinct fields.

| Site | CP 1.60 | CoM 1 | Arguments |
|---|---|---|---|
| Constructor snapshots mutations | `0x8EE0C` | `0x8EE11` | M, before CoM's Catapult persistent mutation assignment |
| Constructor builds enchantment locals | `0x8F007` | `0x8EFEF` | P OR I; CoM first strips item Land Link at `0x8EFFA` |
| Constructor calls Specials | `0x8F2A2` | `0x8F0E8` | bu, P OR I, M |
| Battlefield builds delta | `0x909CB..0x90A09` | `0x906F4..0x9072F` | D = (P XOR B) AND B = B AND NOT P |
| Battlefield calls Specials | `0x90A1D` | `0x90743` | bu, D, **zero** mutations |

Each Specials body is entered twice in a constructor→battlefield sequence. A particular
write need not occur twice. An enchantment branch runs in the constructor when its bit is in
P OR I, and in the second call when in D. A persistent bit is excluded from D, but an item-only
bit is not excluded by that formula: overlap with B can enable both invocations. Admission and
the population of B determine which cases actually occur; this table does not invent them.
Arguments are snapshots: a write to B inside Specials does not change its current `ench` value.

The binary MD5s were checked against [the binary index](../MoM%20binary%20analysis.md#the-binaries).
Existing [R6.1a](./R6.1a.evidence.md), [R6.1b](./R6.1b.evidence.md),
[R6.1c](./R6.1c.evidence.md), [R6.1d](./R6.1d.evidence.md),
[R6.1e](./R6.1e.evidence.md) and [R6.1g](./R6.1g.evidence.md) own the reconstructed extents.

## Reading the tables

- **C**: constructor path only; not necessarily inside Specials.
- **R**: battlefield path only, outside Specials unless stated.
- **E**: both Specials invocations reach the test; writes depend on that invocation's `ench`.
- **M**: both reach the mutation test, but only C can pass with supplied mutations. The CoM
  Undead exception is explicit below: Blood Lust can create local mutation state during R.
- **H**: HP is calculated by distinct constructor and battlefield helpers, each rebuilding
  from its own inputs; do not run the calculator's additive HP step twice on one accumulator.
- **X**: neither; a cast-handler write is flattened into `c` by the current calculator.

Addresses below are file offsets in the table's build and identify existing source branches,
not new binary interpretations. Compound rows deliberately retain multiple source sites: one
calculator key is not always one engine block. Other predicates still apply at every site.

## Operations hidden by the current keys

The tail's Holy Arms grant, Fantastic/race weapon upgrade and to-hit normalization are
**both-call** operations, independent of `ench`. They are not separate current `c:` keys.
CP sites are `0x8F197..0x8F1BE`, `0x8F213..0x8F235`, `0x8F23A..0x8F266`;
CoM sites are `0x8F15C..0x8F18D`, `0x8F1DB..0x8F1FA`, `0x8F1FF..0x8F22B`.
CP Holy Arms additionally checks local mut and battle Fantastic; CoM checks persistent unit type.
The Holy Arms write changes B, so it can supply D to the second call without supplying the
first call's already-copied `ench`. A grant first made within R cannot change R's copied argument.
CP's independent Death-race immunity block at `0x8F817..0x8F828` also runs both calls.

HP helpers are a separate schedule: constructor calls `BU_HitPoints` at CP `0x8F2FF` / CoM
`0x8F2FB`; battlefield calls `BU_Recompute_Hit_Points` at `0x90B7C` in both builds. The latter
starts from template HP and combines P OR B OR I at `0x8E884..0x8E89E`, rather than D. Constructor Lion Heart/Black Channels tests read P; item Lion Heart has
its separate hero-item fallback, documented in the helper.
Its level thresholds are at `0x8EA3B..0x8EA5B`; constructor thresholds are CP
`0x8E7EE..0x8E80D` (shared ladder, including heroes) / CoM `0x8E75D..0x8E767` (non-hero ladder). Lion Heart constructor sites are CP
`0x8E70D..0x8E712` / CoM `0x8E699..0x8E6BD`; battlefield sites CP `0x8E940..0x8E95E` /
CoM `0x8E930..0x8E95E`. CP Black Channels HP is at `0x8E6EC..0x8E6EF` and
`0x8E91F..0x8E92F`. Thus an E+H row cannot be implemented by replaying its complete current
calculator step at each Specials call. Hero/item details remain their existing evidence scope.

## Consequences for F277.2 and F277.3

CoM's summon-route race/Fantastic stores (`combat.c` `0x75D56/0x75D65/0x75D6C`) occur
after Load_Battle_Unit returns and before battlefield effects. Constructor Chaos Surge,
Survival Instinct and Eternal Night therefore precede those stores; node/aura and battlefield
Darkness/Supreme Light follow them. This is a caller-boundary finding, not a new decision about
all cast/recalculation schedules. Raise Dead follows its own handler route.

The design needs invocation-specific arguments, mutations produced within an invocation,
separate source blocks hidden in compound keys, and explicit ordering around calls. A blanket
“run all c steps twice” or “all non-ench steps run twice” is contradicted by this census.
Even the current late Eternal Night rank cannot identify its caller. No choice among the
F277.2 representation alternatives is made here; that remains a human decision.

The existing admission/source gaps (including the proposed P1/P2/P8.1 investigations in the
control census) remain open. No universal before-every-cast timing or Raise Dead field-retention
claim is established here. F277.3 owns schedule implementation and numerical consequences.
