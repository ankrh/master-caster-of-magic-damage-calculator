# D28 — `Auto_Move_Unit` and CP Wall-of-Fire movement parity

## Scope, identity, and acceptance

This durable evidence package covers only:

- MoM 1.31 and MoM CP 1.60 `WIZARDS.EXE`;
- `Auto_Move_Unit` `[0x8A90D,0x8B30D)` in both builds;
- the build-specific body at `0x89448`: MoM 1.31
  `[0x89448,0x89505)`, CP 1.60 `[0x89448,0x89454)`.

CoM 1 and D22's Fireball record are out of scope.  Calls and data outside these
extents were inspected only to bind dependencies.  ReMoM and prior repository
documents were used for vocabulary/orientation after the raw control flow was
decoded; all conclusions below were rechecked against the pinned executables.

No acceptance criterion needed weakening or objective-scope expansion.  Both tracks strengthened
the cross-build comparison: the merge treats the old and new meanings of exported overlay entry
`0390:002A`, and every other differing run inside `Auto_Move_Unit`, as required findings.  In
1.31 the entry is an insertion-sort body; CP repurposes it as the Wall-of-Fire thunk.

## Cross-build findings and calculator relevance

### Exact CP-only chain and trigger

Byte-backed fact:

1. At each accepted, non-attack path step, after the defender/stone-wall
   stay-inside-city restriction, CP executes `0x8AF6B: E8 DA E4`, a near call
   to `0x89448`.
2. The helper executes `56 / 9A 43 00 E0 03 / 59`, resolving to
   `Check_Wall_Of_Fire_Attack` at `0x9EDAA`, then `83 7E E0 01 / C3` compares
   the caller's `move_visible` local and returns those flags.
3. The caller's `MOV [bp-0x28],1` does not change flags, so `0x8AF73` preserves
   1.31's visibility branch.  The Wall call itself is therefore independent of
   invisibility/visibility.
4. CP then tests mover `status == BUS_ACTIVE` at `0x8AF78..0x8AF8A`.  A unit
   killed by the Wall skips animation/teleport but reaches the common coordinate
   commit.  The helper is reached only after `target_cgx/target_cgy` were loaded
   from the current path element at `0x8AE2D/0x8AE4C`.
5. Combining those bytes with the independently inspected `0x9EDAA` predicate,
   the extra edge fires precisely for an admitted AI movement path step that
   crosses from outside the city box to a target inside it, when Wall of Fire is

### Calculator decision

No calculator behavior should change for either `mom_1.31` or
`mom_cp_1.60.00`.

- Fact: MoM 1.31 has two incoming edges to `Check_Wall_Of_Fire_Attack`: the
  interactive movement-phase call at `0x6CF07` and the attack-phase call at
  `0x99670`.  CP retains both and adds the `Auto_Move_Unit` movement-phase edge
  at `0x89449`, reached by D28's call site `0x8AF6B`.
- Fact: the CP edge is therefore a parity addition to the tactical AI/automatic
  path executor, not the invention of movement-phase Wall damage.  Both builds
  already resolve Wall damage while traversing interactive movement paths.
- Fact: the two movement executors differ after lethal Wall damage.  The shared
  interactive executor's `0x6CF1F: 7E 02` path skips coordinate commit, whereas
  CP's `Auto_Move_Unit` path at `0x8AF8A: 75 E9` reaches the common coordinate
  commit at `0x8B0CC`.
- Fact: the calculator's scoped transaction is one melee/ranged exchange and
  deliberately excludes unit positioning and movement.  It already models one
  Wall phase for a melee attacker and none for a ranged attacker.
- Inference: modelling either movement executor would require adding
  path/position history outside the calculator's stated one-exchange scope.  It
  must not be represented by another Wall phase; doing so would double-count a
  crossing in exchange scenarios and invent movement state the input contract
  does not carry.

Thus the correct before/after statement is preservation: `mom_1.31` and
`mom_cp_1.60.00` continue to resolve the existing one Wall-of-Fire melee phase;
D28 shows that movement-phase Wall resolution is outside calculator scope in
both builds, while CP equalizes the automatic and interactive movement paths.
