# F271.1 — Derivation input callers and source intent

Historical inventory against the F279.2-approved tree. The line locators and batch ownership
below describe the migration's starting state, not remaining work. F271.2–.6 completed the
conversion and removed the merged input API; see [the final flow](F271.source-input-flow.svg).
The source-intent distinctions remain useful; recheck code rather than treating this snapshot
as a current caller census.

## Boundary and completeness

The boundary is `deriveUnitStats(input)`, including `ctx.` calls, lexical bindings obtained
with `read`/`vm.runInContext`, forwarding functions, and calls inside evaluated strings.
Search `Calculator`, `tools` and `tests`, not only direct `deriveUnitStats(` matches. A
comment/string mention is not necessarily a call: `drift_class_sweep.js:342` names a function
for static reader analysis; `stats_origins.js:492` names it in a diagnostic. Neither is a
merged-input producer. The measurement artifact `.reviews/F271.1/source-inventory.json`
keeps lexical locations, candidate maps and current definition metadata; it is a locating aid,
not an AST/dataflow proof or a source-intent oracle.

Reviewed forwarding boundaries include `baseUnitInput`, local `makeUnit`/`derive`/`modern`/
`warlord` factories, `psychoForceInput`, `warlordUnit`, `f20Input`, `f25Unit`, scope/sweep
`baseInput`, `enumerateCases`, and page `readMatrixCustomUnitStats`. Evaluated calls in
`preset_applier`, `backlog_checks`, `card_state_projection` and page tests are included.
Existing card/preset producers already retain origins and remain on that path.

Only the **input** merged map is retired. The returned calculated `abilities` record, resolver
objects, direct helper/step records, roster ability-name lists, stored card maps and fixture
control maps have different meanings. Do not rename them in a global replacement.

## Source resolution and sweep coverage

The current dual-source keys are `holyBonus`, `resistanceToAll`, `fear`, `magicImmunity`,
`missileImmunity`, `teleporting`, `immolation`, `undead`, `invisibility`. Definition names identify
the possible origins, not the origin of a collapsed value. Numeric Holy Bonus/Resistance to All
mean **provided** in the innate half and **received** in the marked half. For the seven flags,
the marked controls include Cloak of Fear, Hillfort and Planewalking; do not label every marked
value with its intrinsic ability name.

For explicit scenario maps, keep the scenario's stated source: attack/gaze/touch magnitudes,
owner retorts and intrinsic properties are innate; selected spells and named received/building/
reform controls follow their producer's marked boundary. These boundary names are not a claim
that every marked input is literally a spellcast: the approved executor design separately
places training and external producers. Do not move those producers into a new runtime API in
this caller-only migration.

Unknown-definition keys are not automatically made casts. `flameBladeWarlord` in the stale-key
probe (`derive_unit_stats:233`) and uncontrolled/derived package fields in `ability_origins`
and `warlord_abilities:465` deliberately test raw statements/refusals. Keep those raw fields
innate and preserve the exact assertion; do not replace them with a valid producer control.
Output-only names on direct resolver/step records are outside this conversion entirely.

Sweeps must carry a source tag from the enumerated control **before** collapsing to calcKey.
Solo cases cover innate-only and marked-only where those controls exist; combination cases
retain independent values in both halves, including unequal provided/received magnitudes.
An old one-value duplicated into both halves is not a combination witness. Preserve existing
explicit opposite-half refusal probes and report changed case/refusal/reachability counts.
The original generators already identify ability versus enchantment definitions, so this
requires no user invention of origin. Do not implement a replacement generic reverse splitter.

**Use separate-origin variants for the listed source-neutral probes where the existing
consumer assertion applies to each origin.** This clarifies their generic consumer claim without inventing a single historical
origin or asserting two sources at once. It adds cases to existing checks, not a new suite.
The alternative is to narrow each listed probe to one chosen origin and relabel its claim;
that gives less coverage and would need a choice unsupported by the current assertion.
No combined-origin scenario is inferred; explicit combination coverage remains with the
existing source matrices and sweeps. Keep current expected consumer assertions; if separating
origins exposes a difference, report it and its source evidence before changing expectations.
Where one assertion contains two independently source-neutral inputs, exercise their
Cartesian origin combinations: Fear versus Magic Immunity in `backlog_checks:431–464`,
Immolation versus Magic Immunity in `phases:1229–1246`, and attacker/defender Fear in
`phases:1550–1564`. Include cross-origin pairings as well as matching-origin pairs; each key
still appears in exactly one half per unit. This preserves the unrestricted consumer claim
without asserting simultaneous origins for a key or changing numeric expectations.
These are ordinary cases within the authorized migration, not a new product ruling or an
automatic approval gate. Ask for a decision only if the desired semantic claim remains
unsettled or preserving it requires a scope/expected-behavior change.

`resolution_steps`' named “Undead conversion” is already identified as the conversion request,
so it is marked and not part of A. The DOS `dosValues` provider case is explicitly innate.
