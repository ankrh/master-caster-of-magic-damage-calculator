# F257.1 — The Marionette ascension block's retort tail

Reading of the retort-gated writes at the end of `UnitCalcPre.CAS`'s Marionette ascension block,
and the ruling on how a wizard retort enters the calculator's inputs. Filed 2026-09-09.

Reference tier: re-verify against the shipped scripts rather than citing this file as authority.

## Version scope

**Warlord 1.5.12.9 only, for every write below.** Base CoM2 1.05.11 ships a twelve-line
`UnitCalcPre.CAS` whose whole body is one Iron Skin item-power test
(`Reference docs/Script source/CoM2 1.05.11 base/UnitCalcPre.CAS~"IF GETITEMPOWER(U,74)>0 THEN {"`),
so it has no Marionette region, no ascension block and no retort tail. The three DOS builds have no
scripts at all. The retort *ids* are Warlord's own — `MASTER.CAS~"SageMaster=2"`,
`MASTER.CAS~"Artificer=13"`, `MASTER.CAS~"Astrologer=15"`, `MASTER.CAS~"Charismatic=17"`,
`MASTER.CAS~"Enchanter=18"` — and slot 18 is not even the same retort in the other set, which names
it Spellweaver (`Reference docs/Script source/CoM2 1.05.11 base/retorts.ini`, `[18]`). Nothing here
may be widened past Warlord on the assumption that the modern builds agree.

## The enclosing gate

Four tests stand between the file entry and any write in the tail, and every one of them is already
a term the calculator carries:

| Test | Location | Calculator term |
|---|---|---|
| `IF ( ISHERO(U) = 0 ) THEN { GOTO "NOTHERO"; }` | `UnitCalcPre.CAS!NOVAMPIRISM!+3 "IF ( ISHERO(U) = 0 ) THEN { GOTO"` | `u.ishero` |
| hero type 48 | `UnitCalcPre.CAS!NOVAMPIRISM!+6 "IF (GETSTAT(U,SHeroID,1)<>48) THEN { GOTO"` | `u.herotype === MARIONETTE_HERO_TYPE_ID` |
| no Channeler retort leaves the branch | `UnitCalcPre.CAS!NOVAMPIRISM!+8 "IF (RETORT(W,Channeler)=0) THEN { GOTO"` | `abilities.channeler`, i.e. `marionetteOwned` |
| ascension state is 2 | `UnitCalcPre.CAS!ENDOFMARIONETTESPELLSELECT!+63 "IF (SPELLSTATE(W,SMarionetteAscension)<>2) THEN { GOTO"` | `abilities.marionetteAscension`, i.e. `marionette.ascended` |

So every step F257.3 adds carries `marionetteOwned && marionette.ascended && <the retort>` as its
`when`, exactly as the fifteen `b:marionette:ascension:*` steps carry
`marionetteOwned && marionetteOwnedGrantFires(...)` today.

The tail as a whole is `UnitCalcPre.CAS!ENDOFMARIONETTESPELLSELECT!+111..+164 "IF RETORT(W,Alchemist) THEN {" "}"`
— sixteen `IF RETORT(W,…)` blocks. Five of them write something the calculator's **record** can
receive and are read below; four more reach a calculator **input** of the other shape and are the
subject of *The two input shapes* further down; the remaining seven write hero-ability ranks and
overland stats the calculator holds in neither form (`HAAEtherMaster`, the five `HAChosenOf…`,
`HANoble`, `HASupplycommander`, `HAIrresistibleCharge`, `HALogistics`, `APlaneShifting`, `SMaxMP`),
as does the unconditional `SETHEAB(W,48,HAArcanePower,2)` at the head of the same region. The retort-tail
comment in `Calculator/stats_sequence.js`, immediately above the `marionette:strayedPackage` step,
states the same exclusion and is **wrong on the four**: it says the rest "are hero-ability ranks and
overland stats the record does not hold at all" and lists `HALeadership`, `HALogistics`,
`HAPrayermaster` and `HADivineBarrier` among them. Three of those four are `*Aura` controls today.
F257.3 corrects that comment where it stands.

## The writes

**Gate** is the block's opening `IF`; **write rank** is the line the write is on, and the write rank
is what F257.3 orders steps by. Each `IF` is its own gate, so a per-write citation already satisfies
the audit's gate requirement without reaching outside the block; the branch entrance and the
ascension gate are the two further spans a step cites, in the shape the existing ascension steps use.

| # | Gate | Write rank | Retort | Write | Selector | Calculator key | Citation |
|---|---|---|---|---|---|---|---|
| 1 | `+114` | `+115` | Sage Master | `SETHEAB(W,48,HASage,2)` | wizard hero record, hero type 48 | `sage` (rank, number) | `UnitCalcPre.CAS!ENDOFMARIONETTESPELLSELECT!+114..+116 "IF RETORT(W,SageMaster) THEN {" "}"` |
| 2 | `+149` | `+150` | Artificer | `SETHEAB(W,48,HAMechanicalMaster,2)` | wizard hero record, hero type 48 | `mechanicalMaster` (rank) | `UnitCalcPre.CAS!ENDOFMARIONETTESPELLSELECT!+149..+151 "IF RETORT(W,Artificer) THEN {" "}"` |

| 4a | `+158` | `+159` | Charismatic | `SETHEAB(W,48,HACharmed,1)` | wizard hero record, hero type 48 | `charmed` (boolean) | `UnitCalcPre.CAS!ENDOFMARIONETTESPELLSELECT!+158..+161 "IF RETORT(W,Charismatic) THEN {" "}"` |

`SETHEAB W,H,A,V` "sets the hero ability A of hero H for wizard W to the value V", `1` normal and
`2` super (`Reference docs/Script source/CAS reference/Scripts.TXT:693`). `48` is the Wanderer, the
only hero the enclosing gate admits, so the write lands on the unit being calculated.

### Six writes, not five

The item body names five. The Charismatic block holds **two** `SETHEAB` calls, and the second,
`HALucky`, reaches `lucky`, the key with the largest combat consequence in the tail. It is **not**
that key's only owned-branch producer: `b:marionette:books:lucky` writes it from
`SETSTAT(U,ALucky,0,1)` at `UnitCalcPre.CAS!ENDOFMARIONETTESPELLSELECT!+47..+49 "IF (BOOKS(W,Life)>4) THEN {" "}"`,
five or more Life books. Charismatic is a second, independent route to the same flag, and the two
agree where both fire. F257.3 positions six steps in five gated blocks, or states why it drops 4b.

### How each write differs from the package grant the unit already has

The strayed branch (`UnitCalcPre.CAS!STRAYEDMARIONETTE!`) writes `HASage 2`,
`HAMechanicalMaster 2`, `HARitualMaster 2`, `HACharmed 1` and `HAArcaneWard 2` with the **same
values**, and `EncSpellLock` after its skip label. Two differences, and only one of them is real:

1. **The branches are mutually exclusive.** The strayed writes are reached only when the wizard has
   no Channeler retort; the tail only when it does *and* the ascension state is 2. A unit never
   takes both. So on the owned branch these five retorts are the only region-`b` producer of `sage`,
   `mechanicalMaster`, `ritualMaster`, `charmed` and `spellLock`. `lucky` is the exception:
   `b:marionette:books:lucky` also writes it, so Charismatic is a second route rather than the only
   one.
2. **The strayed writes carry a per-write `IF (GETHEAB(U,…)=0)` skip and the retort writes carry
   none.** The strayed block is first-writer-wins — a unit holding Sage 1 keeps 1 — while the tail
   overwrites. **This difference moves no number in any state the page can reach**: the three ranks
   (`sage`, `mechanicalMaster`, `ritualMaster`) have no control and no other producer, so nothing
   can stand there for the overwrite to displace, and the other three writes set booleans to `true`,
   where overwrite and skip agree.

### Evidence gap: `HALucky` to `U.Lucky`

`HACharmed` needs no fold — the modern engine reads the wizard hero array directly,
`Wizards[BaseUnits[u].owner].Hero[Units[u].herotype][HACharmed] > 0` at `$00595BC0`
(`Caster binary/CoM2 binary - resolution helpers.md`, and
`Combat.ResolutionHelpers.R5.2e.evidence.md`), so the calculator's `charmed` key stands for exactly
that array entry. `EncSpellLock` is written on the unit's own permanent enchantment array, the same
write `b:marionette:spellLock` already makes. The three ranks are carried as ranks and read by
nothing.

`HALucky` is the exception. The block that spends it is `if U.Lucky then` at
`$0059DDC3..$0059DEC2` (`Units.RecalculateUnits.pas`), and the comment there states it: "Lucky is a
direct unit boolean, not an enchantment-array test at this point." The candidate bridge — the only
one this reading found, not the only one that could exist — is `@Units@ApplyHeroBonus`
(`$005992CC..$0059991F`, called at `$0059ACB7` from `RecalculateUnits`, region `c`, after the
`UnitCalcPre` hook), whose **body is not reconstructed**. Its extent is listed in
`D29.evidence.md`'s TD32 adjacency table, but that dossier locates and bounds
`@Units@ApplyMagicWeapons`, and the two callers it enumerates are that routine's. So the claim that
`SETHEAB(W,48,HALucky,1)` gives the Wanderer the +10 To Hit / +10 To Block / +1 Resistance the
calculator's `lucky` key carries" rests on inference, not on a read. It is recorded as `D37` in
`Reference docs/Engine verification evidence.md`.

This matters because 4b is the write with the largest numeric consequence in the tail. F257.3 either
reconstructs `ApplyHeroBonus` first (Method B) or positions 4b as a declared inference.

## The two input shapes, and which of them each retort takes

**The question is a false alternative: the calculator already has both shapes, and the tail splits
across them on a discriminator the source states.** The recommendation is therefore *five booleans*
for the six record writes, in the existing `marionetteConjurer` shape, and *nothing new at all* for
the four aura retorts, which the `*Aura` stated-value controls already carry.

`heroabil.ini` is the discriminator, and it is read rather than argued. Its own legend gives the
scaling rule: "Amount gained per level equals Bonus/BonusDiv rounded down."

| Ability | `Bonus`/`BonusDivisor` | `Levelscale` | Shape |
|---|---|---|---|
| Charmed `[14]`, Lucky `[18]` | `0`/`1` | `No` | flag — the magnitude *is* the write, so the **cause** is statable: a boolean control |
| Divine Barrier `[4]`, Soul Linker `[6]`, Leadership `[16]`, Prayermaster `[21]` | `1`/`3`, `5`/`2`, `1`/`3`, `1`/`2` | `Yes` | scaled — magnitude is `f(level, super)` over a friendly-stack maximum, so only the **effect** is statable: the four `*Aura` numeric controls |
| Ritual Master `[1]`, Sage `[22]`, Mechanical Master `[31]` | `6`/`1`, `10`/`1`, `2`/`1` | `Yes` | scaled, and carried as the rank itself — zero readers in `combat_*.js` and `engine.js` |

That is why F244.3g was right to decline `HASoulLinker` and why declining it says nothing about the
six here. Soul Linker is level-scaled and stack-maximised, so a step would have no number to write;
Charmed and Lucky are flags whose written value is in the script.

The premise the item was filed on — "a wizard retort is none of [the enumerated input kinds]" — is
true of the contract's text and already false of the build. The card carries twelve wizard-level
inputs today, five of them retorts (F257.2 corrected the count from nine: this table had missed
the three retort controls outside the Marionette cluster):

| Control | What it is | Where |
|---|---|---|
| `guardian` | the Guardian retort | `enchantments.js`, CoM 1 & 2 & Warlord |
| `tactician` | the Tactician retort | `enchantments.js`, CoM 1 & 2 & Warlord |
| `artificer` | the Artificer retort | `enchantments.js`, Warlord only |
| `channeler` | the Channeler retort | `enchantments.js`, Warlord only |
| `marionetteConjurer` | the Conjurer retort | `enchantments.js`, Warlord only |
| `outlanderWizard` | the owning wizard is an Outlander | `enchantments.js`, Warlord only |
| `marionette<Realm>Books` (five) | the owner's spell-book count per realm | `enchantments.js`, Warlord only |
| `marionetteBaseSkill` | the owner's base casting skill | `enchantments.js`, Warlord only |

So F257.2's `PROPOSALS.md` amendment regularises what the build already does rather than opening a
new kind of input. Four more booleans on the same per-side ability map cost what
`marionetteConjurer` costs — four, not five, because `artificer` is already one of them.

Why the six do not take the `*Aura` shape. Stating the effect instead of the cause would mean adding
controls for `sage`, `mechanicalMaster` and `ritualMaster`, which have no combat readers at all, and
would leave `lucky`, `charmed` and `spellLock` exactly where they are — which is the *do nothing*
option below, not a different input shape. The cause is the cheaper and more faithful input.

Why the *Input/output contract*'s eligibility rule is satisfied rather than strained. The rule says
every effect is markable on every unit and gated internally, because the matrix applies one effect
across a whole filter. A retort marked on a side means "this side's wizard has the retort", which is
exactly what the matrix's per-side enchantment channel already expresses for `channeler` and
`outlanderWizard`; and the gating is internal in the required way, since a retort mark on a
non-Wanderer, non-Channeler or non-ascended unit is admitted by the control and refused by the
step's `when`. Nothing is disabled.

The honest cost, stated because it argues the other way. **Every number these six writes can move is
already reachable from the card today**: `lucky`, `charmed` and `spellLock` are existing controls, so
a user who wants a Charismatic-and-Enchanter-owned ascended Wanderer can tick Lucky, Charmed and
Spell Lock and get the same combat-relevant record; only the three rank writes would differ, and no
line of `combat_*.js` or `engine.js` reads them. The one place a rank could matter — the strayed package's
`!u.spellLock` gate — is on the branch these writes cannot reach. So F257 as a whole buys
faithfulness of *provenance* (the chain names the retort that caused the value) and not one moved
number, and F257.3's expected digest movement is zero at default inputs and a duplicate of an
already-expressible state at non-default ones. That trade is the user's to make, not an agent's.

## What F257.2 and F257.3 inherit

**F257.2 closed 2026-09-09.** It added *four* controls, not five: `sageMaster`, `astrologer`,
`charismatic` and `enchanter`, beside `channeler` in `enchantments.js`, each Warlord-only with a
`nonRecord` origin row. The tail’s fifth retort is Artificer, and `artificer` is already a
control stating that same wizard fact (`stats_origins.js`, `input:the owner holds the Artificer
retort`), so F257.3 gates the `HAMechanicalMaster` step on it rather than on a duplicate. The
`PROPOSALS.md` entry amending *Input/output contract* is open. Nothing new for the four aura
retorts, and the controls default off, so no number moved.

**F257.3** — six `phase: 'b'` steps at the write ranks in the table above, one per engine write,
each gated on the owned branch, the ascension flag and its own retort, and each writing the value
the script writes with **no** `GETHEAB` skip. Four things it must settle rather than assume:

1. whether `lucky` (4b) is positioned on the `ApplyHeroBonus` inference or held for `D37`;
2. its collision with **F147**, which proposes deleting `sage`, `mechanicalMaster` and
   `ritualMaster` as read by nothing — F257.3 runs first and would add a second writer to each, so
   F147's disposition has to be taken as a whole rather than key by key;
3. the retort-tail comment in `Calculator/stats_sequence.js`, which lists `HALeadership`,
   `HAPrayermaster` and `HADivineBarrier` as things the record "does not hold at all" while three
   `*Aura` controls hold them;
4. whether `lucky`'s two owned-branch producers — `b:marionette:books:lucky` and the new
   Charismatic step — need any ordering relative to each other. They write the same value, so
   probably not, but the chain a user hovers will show both.

F257.2 closed a fifth of them: the `artificer` tooltip, which described the training-time
Mechanical grant alone, now names the Wanderer's Mechanical Master rank 2 as well.
