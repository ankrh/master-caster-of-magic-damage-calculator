# F258.1 — where Eye of Heaven zeroes gaze, and which phase that is

Adjudication only. No `Calculator/` file was changed here; F258.2 executed it. Everything below
describes the calculator **as F258.1 found it**: §2.1’s two wrong copies are gone, the zeroing is
one region-`d` step (`d:eyeOfHeaven:enemyGaze`, `stats_sequence.js`), `gazeDisabled` carries the
Warlord test, and `doomGazeFloorKeeps` no longer exists. §3.3 stays unsettled.

The question F258 asks is whether the calculator is right to put Eye of Heaven's gaze-zeroing at
the `template` seed, because F244.3i made that placement load-bearing: `hasGazeAttack`'s Doom term
now reads `ctx.base.doomGaze`, so the value `a:baseCopy` publishes decides whether the DOS Chaos
Channels breath conversion is admitted.

**Answer, in one line: the only gaze write in the shipped Warlord script set is in `UnitCalc.CAS`,
which is region `d`; and no DOS build has a spell or named feature called Eye of Heaven.**

## 1. The engine write

`UnitCalc.CAS!IMMUNETOROT!+8..+11 "IF (HASCOMBATGLOBAL(W,CGEyeOfHeaven,2)>0) THEN {" "SETSTAT(U,SDoomGaze,0,0);"`,
under the section comment one line above it:

```
  : New combat enchantment "Eye of Heaven", is also shut off gaze attack of opponent :
  IF (HASCOMBATGLOBAL(W,CGEyeOfHeaven,2)>0) THEN {
   SETSTAT(U,SStoningGaze,0,100);
   SETSTAT(U,SDeathGaze,0,100);
   SETSTAT(U,SDoomGaze,0,0);
  }
```

**"The only one" is a search result, not something the block asserts.** Grepping the three gaze
field names `SStoningGaze|SDeathGaze|SDoomGaze` across every `.CAS` in
`../Script source/Warlord 1.5.12.9/` returns hits in exactly two files: `MASTER.CAS` (3 — the
constant definitions) and `UnitCalc.CAS` (3 — the three lines above). A case-insensitive `gaze`
search over the same set adds only the `UnitCalcPre.CAS` comment quoted in §1.1. So within the
shipped Warlord script set this is the sole gaze write; the claim is scoped to that set.

Three facts the block carries:

- `CGEyeOfHeaven` is combat-global 21 (`MASTER.CAS~"CGEyeOfHeaven = 21"`), a Warlord addition. The
  `I=2` argument selects the wizard's **current opponent's** combat global
  (`../Script source/CAS reference/Scripts.TXT:387-391`), so the block fires on the unit whose
  *enemy* holds the enchantment. That is what `enemyEyeOfHeaven` means.
- `100` is the "no gaze attack" sentinel rather than a save modifier of 100. The field comment
  states this for `SStoningGaze` only (`MASTER.CAS~"SStoningGaze=38"`); that `SDeathGaze` takes the
  same convention is read off this block using the same value for it, not off the comment.
- The block is behind `IF (TACTICALCOMBAT=0) THEN { HALT; }`
  (`UnitCalc.CAS!IMMUNETOROT!+3 "IF (TACTICALCOMBAT=0) THEN { HALT; }"`), so it does not run in
  strategic combat.

### 1.1 The other unit-recalculation block writes no gaze

`UnitCalcPre.CAS!ENDOFCOMBAT!+2..+5 ", all friendly units gain True Sight while enemy lose all gaze ability :" "}"`
grants `EncTrueSight` under `HASCOMBATGLOBAL(W,CGEyeOfHeaven,1)` — the friendly side, `I=1` — and
nothing else. Its comment names the gaze half of the enchantment; **the comment is not the write.**
`stats_sequence.js`'s `b:eyeOfHeaven` transcribes that block and is correctly limited to the flag.

This says nothing about the enchantment's other scripts: casting, duration and expiry are handled
elsewhere (`COSpell.CAS`, `EnterCombat.CAS`, `CombatEndTurn.CAS`, `OverlandEndTurn.CAS`,
`EnterGame.CAS` all name `EyeOfHeaven`). None of them writes a gaze field, per the search above.

## 2. The phase is `d`, not `template`

Three independent statements put it there:

- **The calculator's own phase definition.** `Calculator/steps.js:35,37` defines region `b` as
  "precalc, in `UnitCalcPre.CAS`" and region `d` as "magic calc, in `UnitCalc.CAS`". Phase is a
  provenance label (project `CLAUDE.md`, *Architecture*), so a write in `UnitCalc.CAS` is a `d`
  write by that definition alone.
- **The engine evidence behind that label.** `UnitCalc` is the second script hook, at `0x5A65D7`
  (`./CoM2 binary - unit recalculation.md:20`), and the five-region table assigns that hook to
  region `d` (`:31`).
- **Order within the file.** CAS executes statements in source order except where an explicit
  `IF`, `GOTO`, loop or `HALT` changes the path (`:261-265`).

Its **rank within** `d` is the tactical late-override band — after Colossal Strength, Vampirism and
Shadow Strike, after the post-magic Outlander block, and before Hierophany. In the shipped
`Warlord 1.5.12.9` file: Colossal Strength opens at `:1223`, the Outlander block closes at
`!NOTCOMBATOUTLANDER!` `:1440`, this block runs `:1475-1480`, and Hierophany opens at `:1547`.

> **Note on the region-`d` map in `./CoM2 binary - unit recalculation.md`.** Its line bands are
> **`Warlord 1.5.12.7`** numbering, which that section declares at `:266-276` — 1.5.12.7's
> `UnitCalc.CAS` is 1667 lines against the shipped 1.5.12.9 file's 1659, and the Eye of Heaven
> block is at 1484 there rather than 1475. F258.1 first "corrected" four of those rows to shipped
> numbering and reverted it: the rows were right, and the edit would have left the table
> mixed-basis. This is exactly why the citation grammar prefers label anchors — `!IMMUNETOROT!+8`
> resolves in both releases; a line number does not.

### 2.1 The calculator carries the zeroing twice, and neither copy is at `d`

`Calculator/stats.js:1239` (`const gazeDisabled = enemyEyeOfHeaven;`) feeds `baseGazeRanged` and
`baseDoomGaze` (`stats.js:1898,1903`), which `template:stat:base` writes onto the record
(`stats_sequence.js:87`). That is copy one, at the seed.

Copy two is the region-`e` floor. `stats_sequence.js:2320-2324` says so outright: the modern tail
"names no Doom Gaze field at all — its floor list is Defense, melee, Ranged, Thrown and the two
Breaths", and the modern arm of `doomGazeFloorKeeps` exists **only** to carry Eye of Heaven's
zeroing. So an engine write that lives in `d` is applied once far too early and once one region too
late, and is modelled nowhere at its own rank.

**The engine's order.** Region `a` copies the permanent record's unzeroed gaze into the calculated
record; regions `a`–`c` and early `d` operate on that calculated copy; only then does Eye of Heaven
zero it, with region `e` still to follow. The permanent record is never zeroed at all.

**What that costs today.** For a version-valid Warlord input the displayed gaze values still come
out at 0 either way, because region `e` re-applies the zero (`stats.js:1924`,
`stats_sequence.js:2323`) and resolution strips the three gaze abilities (`stats.js:2611`). Scoped
to that state, no region-`c`/`d` step reads `u.gaze` or `u.doomGaze` and writes a different field —
the DOS True Light block at `stats.js:2231` writes gaze back to gaze, like the rest. What the seed
placement does corrupt is **the permanent record `a:baseCopy` publishes** and the derivation chain
the tooltip shows, which states a base of 0 where the engine had a positive strength. A consumer
that reads the record rather than the finished value sees the difference, and F244.3i's Chaos
Channels gate is exactly such a consumer — see §4.

**The faithful placement** is a single region-`d` step ranked in the late-override band. `template`
would then seed the unzeroed strength, and the modern arm of `doomGazeFloorKeeps` would lose its
`gazeDisabled` term, which is the whole of what that arm currently is.

## 3. No DOS build has an Eye of Heaven — and what that does and does not establish

### 3.1 Supported: exact-name absence, in all three builds

- Repo-wide case-insensitive search for `eye of heaven` / `eyeofheaven`, excluding `.git`,
  `node_modules` and `.reviews`: every hit is a Warlord or CoM2 file, a `Calculator/` file or
  `TASKS.md`. No DOS-side file — not `../DOS reconstructed/*`, not `../MoM binary analysis.md`,
  not `../CoM helptext.txt`, not `../CoM1manual.HTML`, not the DOS rosters.
- The F258.1 reviewer independently enumerated all 215 spell names in each pinned `SPELLDAT.LBX`,
  hashes matching `../MoM binary analysis.md:17` and `../DOS reconstructed/D35.evidence.md:11`:
  **none of MoM 1.31, CP 1.60 or CoM 6.08 contains a spell named Eye of Heaven**, and exact-name
  scans of all three `WIZARDS.EXE` images found nothing either.
- CoM2 1.05.11 base is likewise clear: no `EyeOfHeaven` identifier anywhere in
  `../Script source/CoM2 1.05.11 base/`, matching `../Version gating census.md`.

That is a per-build result, obtained the same way for each build, so it does not rest on
generalising from one.

### 3.2 Also supported: the enchantment as implemented cannot exist in DOS

Eye of Heaven is a *scripted* combat global (`CGEyeOfHeaven`), and the DOS builds have no script
system at all (project `CLAUDE.md`, *Source routing*: "The DOS versions have neither scripts nor
`UNITS.INI`"). There is nowhere for a `CGEyeOfHeaven` to live. This rules out **this
implementation**; it does not rule out a hard-coded binary analogue under another name.

### 3.3 NOT supported: that no differently named DOS effect suppresses a gaze

The evidence does not settle this, and two things show why the obvious argument is too weak:

- **The DOS combat-enchantment list is not a complete table.**
  `../DOS reconstructed/unitcalc.c:210-238` is introduced at `:19` as the symbolic values used *by
  the landed reconstruction*, not as an enumeration of every slot the engine reads. `combat.c:226`
  defines and reads `BLUR_ATTKR`/`BLUR_DFNDR` at `0x1C`/`0x1D`, which appear nowhere in that list.
- **Grepping assignment forms is not a gaze-write census.** Mind Storm subtracts 5 from
  `bu->ranged` — the shared byte that also carries a gaze's strength — at
  `../DOS reconstructed/unitcalc.c:3808` (MoM 1.31 and CP 1.60; the block is `#if BUILD == MOM131
  || BUILD == CP160`), and the ungated floor at `:4002` then clamps it to 0. That is not an Eye of
  Heaven analogue — it is a strength debuff that also hits melee, resistance and defense — but it
  reaches the same field, and a search for `ranged_type =` and `bu->ranged = 0` would not have
  found it. Resolution-time admission gates would be missed the same way.

Both reconstruction files declare partial landed coverage (`unitcalc.c:6`, `combat.c:3`), so an
absence claim over them is bounded by that coverage.

**What would settle it:** a per-build census of combat-enchantment producers, of every writer of
the shared ranged/gaze byte, and of the attack-admission gates. That is not this subtask.

**Why the narrower claim is enough.** F258.2 needs to know whether `enemyEyeOfHeaven` — the
calculator's input, which models `CGEyeOfHeaven` specifically — should reach the DOS builds. §3.1
and §3.2 answer that: it should not. A hypothetical unrelated DOS gaze-suppressor would be its own
effect with its own control, not this one.

## 4. F244.3i's 16 cases: empty in the source games, **reachable in the calculator**

The two conditions are disjoint by version:

- `ccDosBreathEligibleAt` — the gate that reads `base.doomGaze` — has exactly one caller, the false
  branch of `ccGrantsThisSlot` (`stats.js:1978`), which is consumed only by the Chaos Channels step
  (`stats_sequence.js:515`). It runs only where `ccIndependentChannels` is false, and
  `ccIndependentChannels = isCoM2` (`stats.js:499`, `:30`). **DOS only.**
- Eye of Heaven exists only in Warlord, which **is** `isCoM2`.

**So the intersection is empty in the source games.** It is *not* empty in the calculator, and the
first draft of this file was wrong to call it unreachable state.

## 5. The ungated read is reachable through the matrix

`stats.js:1239` is the one `eyeOfHeaven` read in the calculation layer with no version test. Its
siblings carry them: `stats_sequence.js:1101` (`isWarlord && …`), `stats_identity.js:1007`
(`version.startsWith('com2_warlord')`). `../Version gating census.md` records a round that gated
"`eyeOfHeaven` reads in `stats.js` and `stats_identity.js`" to Warlord; this read was not among
them, because it is spelled as the top-level `enemyEyeOfHeaven` input rather than as the ability key
the sweeps enumerate.

**The two-card UI is protected.** A version-gated control is disabled *and cleared* by
`applyDisabled`, which lives inside `updateTypeVisibility` (`Calculator/ui_abilities.js:471`, the
clear at `:498`) — not inside `updateAbilityVisibility` (`:614`), which only controls presentation.

**The matrix is not.** Matrix rows are persisted separately from the card
(`ui_matrix_properties.js:203`). A Warlord-only row is merely **hidden** after a switch to a DOS
version (`:313`), not removed or cleared, and `matrixHasActiveEnchantment` (`:272`) reads the row
with no version check at all — unlike its sibling `matrixAppliedEnchantments` (`:250`), which does
check `subgroupAllowedForVersion`. `ui_matrix.js:217` and `:302` pass its result straight through as
`enemyEyeOfHeaven`. Nothing clears `matrixPropertyState` on a version change.

So: tick Eye of Heaven in the Warlord matrix, switch to MoM 1.31, and a DOS matrix run carries
`enemyEyeOfHeaven: true`. `baseGazeRanged`, the slot predicates, the Chaos Channels admission gate
and `combatAbilities` all see `gazeDisabled`. **That is a live INV-2 violation and it is how
F244.3i's 16 cases are reached.** It also makes `enemyEternalNight` (`ui_matrix.js:216`, `:301`)
worth checking for the same shape, which this subtask did not do.

**No tool sees any of it.** `enemyEyeOfHeaven` appears in **no tool in the repository** — not
`tools/unit_checks/hidden_control_gating.js` (which exists specifically to assert the derivation
half of the version-gating invariant), not `hidden_control_leak_sweep.js`,
`ability_read_census.js`, `narrow_control_scope_sweep.js` or `derivation_equivalence.js`. Each
varies ability keys and unit fields; `enemyEternalNight` is the only top-level enemy input any of
them sets. This is F259's blind spot seen from the standing checks' side.
