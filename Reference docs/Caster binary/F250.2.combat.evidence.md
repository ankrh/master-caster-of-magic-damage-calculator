# F250.2 — modern combat cast-store reconciliation

The generic combat cast stores and the Warp helper write **`BaseUnits[u].CombatEnchantmentFlags[e]`**, not the base enchantment layer read by `BaseUnitEnchantment`. The containing object is the persistent base unit; the field is its combat source layer. These are separate distinctions. Existing record-accessor and recalculation reconstructions establish that interpretation without new binary reconstruction. No calculator behavior changes here.

## Address result

Let `B=M32[0x709188]`, `u` be the checked unit index 1..40000 and `e` the checked enchantment index 1..100. The actual multiplication is checked `u*0x1E1`, then effective-address scaling by 4; the simplified stride is 0x784.

### Record ownership and recalculation (existing-source reconciliation)

[F264.1's record-base provenance](F264.1.evidence.md#record-base-provenance) binds displacement
0x1AC1798 to `BaseUnits` through the named `GetBaseUnitData` accessor. Its read table already
maps 0x1AC1D68 plus the enchantment index to that record's `CombatEnchantmentFlags`.
Subtracting the known record base gives 0x5D0+e (the one-based array starts at offset 0x5D1).
The base getter instead uses 0x508+e, the `EnchantmentFlags` layer at offset 0x509.
Thus a combat-layer store is a write within `BaseUnits`; it is not a write confined to the
calculated `Units` object, nor is it a store to `BaseUnits.EnchantmentFlags`.

[RecalculateUnits](Units.RecalculateUnits.pas) at 0x599A8D–0x599B30 copies the complete base
record into the calculated record. Its 0x599B30–0x599C2D merge combines the copied base,
item, combat and overland layers into `Units.EnchantmentFlags`. The later merge at
0x59DCF2–0x59DDC3 repeats that aggregation after intervening work. Reuse these existing
bodies; they are not missing reconstruction. This identifies the carrier and consumer,
not every caller, clearing event or intervening script write.

WarpCreatureEffect maps opaque 0x40495C(EAX=3) return 0 to index 6 (`EncWarpAttack`), 1 to 7 (`EncWarpDefense`), otherwise 8 (`EncWarpResist`). It retries when that entry is already nonzero, sets a zero entry to 1, and exits without a direct store when its three initial tests are nonzero. No distribution or termination guarantee is inferred from TD32's `System.Random` name.

### Calculated-record immunity guards (existing-source join)

The reconstructed prefix contains an Illusion Immunity refusal at `CombatSpellEffect` entry.
[F250.4](F250.4.modern.evidence.md) supplies the bounded named player call path and Illusion-key
writer, reusing this predicate. [F264.1's accessor evidence](F264.1.evidence.md#record-base-provenance)
identifies calculated `Units` at displacement 0x6426898. Subtracting that base from the
prefix's 0x642695C gives offset 0xC4, `illusionimmunity` in the existing
[damage-spell record layout](Spells.DamageSpells.R5.2g.evidence.md).
[SpellTableT](../Script%20source/CAS%20reference/Typedec.pas) identifies spell byte+0x50 as
`Illusion`.

The outer guard family applies to groups {4,12,13,14,16} or explicit spell IDs {5,68,89}.
Within it, group != 4, nonzero spell `Illusion`, and nonzero calculated target
`illusionimmunity` cause the rejection at 0x5C9C43. The jump at 0x5C9C48 goes to cleanup
0x5CBC0E, skipping the common script/recalculation tail. Thus configured Vertigo (group 13)
and Mind Storm (group 14), both `Illusion=True` in the
[versioned records](F250.1.spell-classification.evidence.md), use this refusal if those values
populate the runtime fields and the cast reaches this entry. The [F250.4 loader splice](F250.4.modern.evidence.md)
now supplies the INI `Illusion` key's write to +0x50; reaching that splice and populating the
live runtime table remain conditional.

For the scoped spells, this reads the calculated target after `GetSpellSaveModifier`; it does not prove that
earlier helpers preserve state or establish complete outer targeting. True Sight's group 1
bypasses this guard family, which alone does not prove its full eligibility.

The same layout join identifies the fourth guard as spell `Nonmagic` (+0x5B) = 0 and
calculated target `magicimmunity` (+0xC6) != 0. Group 14 skips this gate at 0x5C9CD3 and
also skips the later resistance call. That is a local bypass, not proof of universal
Magic Immunity admission: other guards and earlier callers still matter. Initial
save-modifier computation occurs for Weakness/Mind Storm even when its eventual resistance
call is skipped. The calculator's blanket refusal must therefore be assessed against the
specific cast path during migration; its provenance is not promoted by this join.

The converter permits groups 1 and 13..16, maps zero +0x90 to−1, and leaves caller-side 1..100 checks to fail before either generic store. The prefix contains all supplied special siblings, including Stasis, Web, Confusion and word copies; these were not elided to simplify the scoped result.

## Continuations and boundaries

- Initial nonzero guard and explicit rejection paths jump directly to cleanup 0x5CBC0E; they skip the supplied common tail.
- A signed nonpositive return from `ResistanceRoll` at 0x5CA0E5 jumps to0x5CBBCA without the subsequent curse store. The tail therefore also runs on this path; it is not success-only.
- Tail order: script bridge at 0x5CBBCD, then `RecalculateUnits` at 0x5CBBDC with AL=1, EDX=ECX=−1 and pushed −1, then conditional movement-helper calls. Called bodies remain opaque here.
- The bridge exports nine raw-named variables, including `SPELLTARGETUNIT`, and calls a runtime-selected script. The separate Mystic Surge call exports `TU`. Script filenames, imported-pointer initialization and actual script behavior are absent.
- True Sight/group1's post-store route is supplied by the [continuation supplement](F250.2.truesight-continuation.evidence.md); the original prefix ends at 0x5CA369.
- Direct effect stores in CombatSpellEffect reload the imported target; WarpCreatureEffect uses its argument, supplied by the shown caller. Caller selection, target identity across opaque calls, guard lifecycle and persistence are not proved.

No direct write to the base-getter region occurs in these supplied instructions. This does not exclude writes in omitted code, other callers, overland code or scripts. All relevant cast provenance entries remain UNVERIFIED: the modern persistent object's combat layer is established, but its equivalence to the calculator's undifferentiated permanent flags, DOS behavior and full named admission is not.
