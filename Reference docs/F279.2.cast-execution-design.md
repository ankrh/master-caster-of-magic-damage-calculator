# F279.2 — Cast requests, records and calculation calls

Design only; no calculator migration is implemented. The shared-routine invocation and
per-effect full-pass policies are already approved in `CLAUDE.md`. The user approved the starting-state, migration-staging and phase-table wording on
2026-09-11; `CLAUDE.md` owns those rulings. [Diagram](F279.2.cast-execution-design.svg).

## Selected design

Use a structural executor with separate records and explicit calls. Wrapping the
current `deriveUnitStats` in a loop is cheaper locally, but it would repeat template/training
work and earlier cast writes, seed admission with future selected effects, and retain the
flat trace's assumption that each source runs once. It cannot support the required claim.

The structural option touches five mechanisms: source-qualified input preparation, record
ownership, ordered request execution, versioned routine schedules, and occurrence-aware
trace consumers. F271 and F279.3a/.3c/.3b already own these changes. Cost grows with the
actual calls and their unit scope; modern combat recalculation includes two unit loops and
an aura boundary. Preserve the compact execution ledger and lazy hover materialization for
matrix runs. No timing estimate, cache, new task or extra compatibility API is implied.

**Starting state.** Follow the fresh-unit starting convention in `CLAUDE.md`, Architecture.
The versioned initialization recipes below implement that convention.

The alternative is to require a complete pre-cast engine-state input, including retained
calculated fields and history-sensitive external state. It can represent more histories but
requires new input/product design beyond the present card. Feeding the current flat final
result into the new executor is not an equivalent substitute.

**Migration staging.** Follow the temporary whole-run selection ruling in `CLAUDE.md`,
Deliberate deviations. The qualification manifest below supplies its coverage decision.

The alternative is to withhold production cutover until every supported dependency has
migrated, while developing the executor against qualified fixtures. It avoids a temporary
selector but delays all production use of the new behavior. Neither choice waives the
all-five-version Holy Weapon pilot's required admission and timing claims.

## Records and execution

Use these concepts as data boundaries, not a second collection of effect definitions:

| Concept | Owns | Does not stand in for |
|---|---|---|
| Inputs/template | Roster/custom base values, explicit innate and training sources | Future requested casts or a historical calculated record |
| Requests | Source-qualified attempted effect, parameters and stable request ID | An already admitted enchantment flag |
| Persistent record | DOS permanent unit fields; modern BaseUnits and its distinct aggregate/item/combat/overland carriers | A collapsed union of every source |
| Calculated record | DOS battle unit or modern Units state at this point in execution | A permanent record alias or a freshly zeroed object on every call |
| External context | Authored wizard/battlefield inputs and separately owned mutable state used/written by calls | Unit effects, invented army positions, or guaranteed immutable globals |

Prepare template/training state once; perform the proposed initial calculation once. Process
the cast-origin requests in the existing manifest's assumed immunity/buff/debuff order, preserving
the declared order within buffs and debuffs. An unmarked control adds no attempted cast.
Innate properties, global grants and recalculation-produced mutations are not manufactured
requests. Keep each at its evidenced producer and time.

For each request, read admission against the actual record and external state at that site,
then execute the admitted handler writes and its versioned continuation. Record admission
separately from whether a write changes a value. A rejected cast, admitted unchanged store,
and later skipped consumer are distinct outcomes. A no-op may still reach a recalculation
tail; a refusal may bypass it. Follow the evidenced branch, not a blanket rule to recalculate
or skip. Carry persistent and retained calculated/external changes into the next request.
Do not replay an earlier request to make its state survive a later calculation.

Entry conditions delimit the modelled application. Modern initialization, animation scheduling
and the opaque `checkspelleffectrequired` helper remain outside the known handler-entry model:
one requested calculator application is not a claim that the renderer applies a spell only
once. DOS opaque calls and live pointer/selector conditions likewise remain explicit. Missing
required admission or retained-state facts block the dependent faithful claim; they are not
silently converted into unconditional admission.

## Versioned boundaries to reuse

The linked source ledgers own exact extents and predicates. These are schedule interfaces,
not replacement reconstructions or proofs about opaque callees.

| Version/family | Initial population and later recalculation |
|---|---|
| DOS, all three | Existing `Load_Battle_Unit` performs a partial type copy, explicit clears/imports and a constructor call; it later imports permanent damage. Do not zero the whole battle record or call a second constructor merely because initial population already contains one. `BU_Construct` resets selected fields; `BU_Apply_Battlefield_Effects` modifies the running battle object and has separate tails/HP rebuilding. |
| MoM 1.31 | The known `BU_UnitLoadToBattle` wrapper does not append the CP/CoM battlefield call. Its constructor also lacks their type-attribute recopy. A proposed ready-for-combat baseline must name its chosen enclosing schedule; it cannot attribute that schedule to this wrapper. Any missing required initial field/schedule remains a qualification gap. |
| CP 1.60 / CoM 6.08 | Reuse their own load-wrapper positions, including the existing battlefield call and CoM caller conversions where applicable. Do not import those conversions into every initialization or copy their position from the current flat region `a`. F277.3 owns remaining summon placement. |
| CoM2 / Warlord | `RecalculateUnits` saves incoming calculated movement before the complete BaseUnits→Units copy, clears EncMagic, merges the copied aggregate/item/combat/overland layers, runs calculation/hooks, builds the aura table, then runs the later loop. Required read-before-copy state must be initialized or supplied, not guessed. Versioned script hooks remain distinct. |

Initial population and a later reset are different operations. For the fresh-unit convention,
the proposed DOS baseline composes the modelled writes of `Load_Battle_Unit` (including its
constructor once), supplied controller/battlefield context, then battlefield effects once.
This composition is the starting-state ruling, not a claim that every version's load wrapper
does it. Do not run CoM's summon wrapper for an ordinary unit. For modern combat, the proposed
baseline is the modelled `RecalculateUnits(True,-1,-1,-1)` schedule after input preparation;
an overland application uses its own pre-application context, not an assumed combat baseline.
The implementation must list fields read before initialization and their input/source owner
for each qualified version/context. This design does not fill unknown movement,
display or caller state with zero, nor claim that a synthetic baseline reproduces an arbitrary
ongoing game. Preserve the existing regular-damage/zero-extra-damage input convention.
Here “required” means a demonstrated dependency of a modelled result, persistent effect or
later admission claim. An engine read of out-of-scope movement/display state does not alone
block a domain: retain it as external/opaque when no modelled dependency uses it. If a later
targeting rule does depend on it, qualify that rule's inputs before enabling that domain.

DOS call composition, where the enclosing sequence supplies the relevant battle object:

| Invocation | MoM 1.31 | CP 1.60 | CoM 6.08 |
|---|---|---|---|
| Constructor → shared Specials | Copied P1 OR I1, saved M1 | Copied P1 OR I1, saved M1 | Copied P1 OR I1 with item Land Link removed as in source, saved M1 |
| Battlefield → shared Specials | Copied D = B2 AND NOT P2, separately saved M2 | Copied D, mutations 0 | Copied D, mutations 0 |

P, I and B are permanent, item and battle masks; subscripts identify each call's own reads.
Later B writes do not alter that call's copied mask. CoM Blood Lust can alter local mutations
and the permanent mutations byte within a call; later calls must see persistent carry.
Constructor work before/after Specials and battlefield modifiers/tails retain
their positions. MoM Holy Weapon/Holy Arms is inline in its constructor; CP/CoM place it in
Specials. A shared routine does not justify duplicating the MoM inline bonus.

The Holy Weapon pilot uses these already recovered application continuations:

| Application | Known continuation and scope |
|---|---|
| MoM / CP combat | Battle-mask writer → three opaque calls → tail's saved-byte handling call → existing local constructor then battlefield calls → byte-7 restoration → two opaque common-exit calls. Preserve the local calls' actual pointer arguments and entry conditions. |
| CoM combat | Battle-mask writer → three opaque calls → local-tail bypass → two common-exit opaque calls → `Calc_Battlefield_Bonuses` with the live argument → existing aggregation tail's constructor/battlefield loop. Its scope is not automatically the target alone. |
| Modern combat | Base combat-source flag writer → script hook → `RecalculateUnits(True,-1,-1,-1)`. Eligible-unit filters and the aura boundary are part of this call. |
| Modern overland | Base overland-source writer → local-tile `RecalculateUnits(False,plane,x,y)` → later script hook. Warlord's later hook can change the carrier; do not add an unobserved post-hook pass. Outer overland UI admission remains separately bounded. |

An ordinary direct cast, an innate/item carrier and a Holy Arms global grant are separate
origins. Reuse their version-specific gates and read times from F236.1; do not infer direct
cast admission from the global-grant predicate or apply both a direct bonus and its consumer.

## When one full pass is safe

Each migrated effect records its actual handler/continuation and compares a proposed shared
calculator pass with that sequence. Compare: (1) records and arguments at entry; (2) reset,
copy, retain and write order; (3) persistent and external mutations; (4) target/all-unit/aura
scope and hooks; (5) later admission/readers; (6) rejected and unchanged-store paths. Final
numeric equality alone is insufficient. Repeating an idempotent bit OR proves nothing about
the surrounding additive writes or a later eligibility test.

Use a shared faithful routine wherever that comparison succeeds. Otherwise schedule the
actual narrower/different calls and name the specific gap or difference. The current full
`deriveUnitStats` is not this routine: `a:baseCopy` snapshots one object into context and the
flat chain mixes input preparation, cast writes and consumers. Modern engine use of a full
pass is evidence for that engine schedule, not proof that the current calculator pass matches.
Project supplied external context explicitly; do not invent an army to claim all-unit
equivalence. An unrepresented dependency limits the affected domain until settled.

## Identity and trace

Keep source identity (`phase:id`, citation, version scope) separate from runtime identity.
Give each request a request ID, each pass/call an invocation ID with parent, routine, arguments
and position, and each write occurrence the invocation ID plus source ID and local ordinal.
Use one increasing execution index across the run; check source order within the routine,
not by globally sorting phases or forbidding a repeated source key.

Admission events identify the record/field/time read, result and reason. Invocation events
show copied arguments and reset/copy boundaries, including both Specials calls when executed.
Writes retain before/after values, destination record and source citation; unchanged or
skipped events remain in the complete ledger. Sparse hover traces and the compact lazy full
ledger project the same executed events. Hover groups repeated writes under their call and
request, without reconstructing a separate history. Attack-specific phases stay outside this
unit-stat schedule. Exact serialized ID spelling is implementation detail, not a new ruling.

## Qualification and implementation handoff

The [control census](Stat%20derivation%20control%20census.md) is the inventory, not an approval
of every cell. A whole-run coverage manifest must identify version, source-qualified input
origins, admitted carriers/readers, initialization/retained fields, schedules, external scope
and applicable exclusions. Compute the dependency closure over **all** inputs and possible
producers: template/innate/training, requested casts, globals, recalculation-produced effects,
and their readers. An absent marked spell does not exclude an innate or global producer.
Record qualified, unresolved and inapplicable cells with evidence; an unresolved cell gates
only configurations that depend on it. No configuration is declared qualified by this design.

| Existing owner | Deliverable / boundary |
|---|---|
| F271.1–.6 | Make source halves explicit across callers; resolve ambiguous intent, then remove the merged-input compatibility path. Do not infer cast requests from a merged flag. |
| F279.3a | Change representation and trace consumers together while preserving current schedules and numbers. One current flat run can be one invocation; no baseline or repeated-pass behavior change yet. Retain source phase labels independently of invocation positions; check TESTS.md's `a:baseCopy` description and propose an update only if its contract changes. |
| F279.3c | Implement records, initialization qualification, outer request execution and pilot call scaffolding. Exercise only evidenced domains; the approved staging ruling controls production selection. |
| F279.3b | Migrate Holy Weapon's admission/writers/readers across all five versions and verify distinct origins, refusal, order and repeated-call cases. Complete required pilot evidence before claiming fidelity; no generic initializer or renderer-lifecycle claim is demanded merely by handler-entry modelling. |
| F277.3 / other named effect owners | Extend their schedules and census coverage, including summon placement and additional grants. Do not repeat known reconstruction or open unapproved preparation rows. |
| F279.4 / F279.5 | Reconcile every census cell/owner, then finish coverage and remove the temporary old-path selection if approved. No blanket exemption for inconvenient origins or no-ops. |

For implementation, numeric corrections belong in preset fixtures; invocation/trace structural
checks belong in the existing step/trace suites. This design-only change requires source/link
and rendered-diagram checks, not runtime suites or a new test file.
